# Execution Events and Feedback v0.1

## Purpose

WP007 upgrades Today from a planning surface into a human execution surface while preserving the domain distinction established in earlier work:

- **Task** — what exists now.
- **Daily Plan / Daily Plan Item** — what was selected for a particular day and revision.
- **Task Event** — an immutable fact describing what actually happened.
- **Task / Plan Item projections** — current state derived from accepted execution commands.
- **User Feedback** — raw user-authored context about a Task / Plan Item / plan experience. WP007 does not interpret it with AI.

## Atomic execution boundary

Browser execution actions do not directly insert `task_events` or update `daily_plan_items.current_state` / execution Task projections. They call `public.record_task_action_v01` with a client-generated Event UUID, target Plan Item, expected execution state, action and optional detail.

The RPC is `SECURITY INVOKER`, pins `search_path = ''`, derives the owner through `auth.uid()`, derives Task and Plan ownership from the Plan Item, locks the target rows, validates the transition, appends the Task Event, then updates the Plan Item and necessary Task projection inside the same database transaction. A failure rolls everything back.

The caller supplies `expected_state` only as an optimistic-concurrency precondition, never as a requested projection. After the Plan Item lock is acquired, the database requires the stored state to still equal that precondition. Concurrent commands opened from the same old state cannot both silently succeed.

## Transition model

| From | Allowed actions | Item projection |
| --- | --- | --- |
| planned | started, partial, done, skipped, deferred, blocked, cancelled | action state |
| started | partial, done, skipped, deferred, blocked, cancelled | action state |
| partial | partial, done, deferred, blocked, cancelled | action state |
| blocked | done, deferred, cancelled, reopened | action state; reopened → started |
| done | reopened | started |
| skipped | reopened | started |
| deferred | reopened | started |
| cancelled | reopened | started |

Task projection rules are deliberately narrower: Done marks the Task done and completed, Partial may update remaining minutes, Blocked marks the Task blocked, Cancel marks it cancelled, and Reopen restores active / clears completion. Skip Today and Defer affect the Plan Item only.

## Idempotency

`p_event_id` is generated by the client with `crypto.randomUUID()`. The RPC serializes the same Event UUID with a transaction advisory lock before its idempotency check. A retry of the same target/action/detail returns the existing Event; reuse of the UUID for a different command raises `Idempotency conflict.`

This contract exists before WP008 so a future offline mutation queue can safely retry the exact same command identifier.

Feedback uses the same principle through `add_plan_item_feedback_v01` and a client-generated feedback UUID.

## Domain mutation guards

Authenticated table grants alone are not the formal execution authorization boundary. Transaction-local `taskring.command_context` values are established only inside approved RPCs, and trigger guards enforce the expected context:

- `execution:v1` — Task Event insert and execution projection updates.
- `publication:v1` — Daily Plan revision / Plan Item structure writes from `publish_daily_plan_v01`.
- `feedback:v1` — feedback insertion.

Direct authenticated Data API insertion into `task_events`, direct Plan Item execution-state mutation and direct feedback insertion are rejected. Daily Plan / Plan Item DELETE grants are revoked so revision history cannot be removed by the browser. Feedback UPDATE/DELETE grants are revoked.

The guard is also `SECURITY INVOKER`; WP007 introduces no `SECURITY DEFINER` shortcut.

## WP006 publication hardening

WP007 replaces `publish_daily_plan_v01` only in the new WP007 migration; the WP006 historical migration remains untouched. The publication RPC sets publication command context before writing revisions and retains all prior revision, ownership, stale-base, duplicate and metadata behavior.

The execution-start guard is strengthened: simple WP006 replanning is rejected if any current Plan Item is no longer `planned` **or** if any Task Event already exists for the active plan. Reopen therefore cannot erase evidence that execution began.

## Feedback

`add_plan_item_feedback_v01` derives `user_id`, `task_id`, `plan_id` and `plan_item_id` from the authenticated Plan Item. It fixes `source = 'frontend'` and `ai_interpretation = null`. Empty content is rejected. Feedback is immutable in WP007 and is displayed as raw user context in History.

## History

`/history` reads Task Events ordered by `occurred_at DESC` and resolves Task titles. It displays action type, time, progress, remaining / actual minutes, reason and note. A simple raw Feedback section is also available. History has no event edit or delete controls.

## Cache and offline boundary

Execution / History query keys are user-scoped. Successful actions invalidate Today, Task management and History surfaces. Authenticated shell teardown removes user-scoped History cache alongside Today and Management cache.

WP007 does **not** add IndexedDB, a mutation queue, offline Event creation or offline Feedback. Offline mutation attempts fail explicitly and nothing is fake-saved. PWA service-worker `runtimeCaching` remains empty; private Auth, Data API, Today, Event, Feedback and RPC responses are not cached in Cache Storage.

## Future work

WP008 may reuse the already-idempotent command IDs for a durable offline mutation queue. Automatic carryover, replanning, AI interpretation, calibration and scheduling remain outside WP007.
